## Требования к среде разработки

- **ESP-IDF v6.0.2** (проверенная версия). IDF v6 вынес `esp-mqtt` из ядра,
  поэтому он подтягивается из ESP Component Registry как зависимость
  (`main/idf_component.yml`).
- **Python 3** и Python-окружение ESP-IDF (venv создаётся автоматически
  скриптом `build_and_flash.sh`).
- **Инструментальные цепочки ESP-IDF RISC-V** (сборка target `esp32c6`),
  версия `esp-15.2.0_20251204`.
- **Компоненты из реестра** (`espressif/cjson`, `espressif/mqtt`): первый билд
  требует доступа к сети. Разрешённые компоненты кешируются в
  `managed_components/` и намеренно коммитятся для воспроизводимости сборок.
- Доступ к последовательному порту (по умолчанию `/dev/ttyACM0`).

`build_and_flash.sh` настраивает окружение ESP-IDF вручную (без
`source export.sh`) и сам определяет пути к toolchain и Python venv. Доступные
переопределения: `IDF_PATH_OVERRIDE`, `IDF_TOOLS_PATH`, `PORT`, `TEST_HOST`.

## Сборка и прошивка

Через `idf.py` (если окружение ESP-IDF уже активировано):

```bash
idf.py set-target esp32c6
idf.py build
idf.py -p /dev/ttyACM0 flash
idf.py -p /dev/ttyACM0 monitor
```

Через канонический скрипт (рекомендуется):

```bash
./build_and_flash.sh build     # чистая сборка (очищает build/ и sdkconfig)
./build_and_flash.sh flash     # прошивка на $PORT (по умолчанию /dev/ttyACM0)
./build_and_flash.sh monitor   # последовательный монитор (нужен TTY)
./build_and_flash.sh all       # build + flash + monitor
./build_and_flash.sh test      # матрица HTTP-эндпоинтов по $TEST_HOST
./build_and_flash.sh clean     # удалить build/ sdkconfig sdkconfig.old
./build_and_flash.sh env       # показать разрешённое окружение
```

Во время конфигурации CMake автоматически:

- генерирует `http_tests_generated.h` из `tests/http_endpoints.csv`
  (`tools/gen_http_tests.py`);
- патчит `fatfs/src/ffconf.h` (`FF_FS_EXFAT 0 → 1`), так как IDF v6.0.2 не
  предоставляет опции Kconfig для exFAT;
- собирает образ SPIFFS из каталога `web/`
  (`spiffs_create_partition_image(...)`).

Подробнее — в [`docs/build.md`](docs/build.md).

## Структура кода

Исходники находятся в `main/`; каждый модуль состоит из пары `.c`/`.h`.
Точка входа — `app_main()` в `main/main.c`.

| Модуль | Назначение |
|--------|------------|
| `main.c` | `app_main()`: строгий порядок инициализации подсистем |
| `pins.[ch]` | Заводские значения пинов (`PIN_DEFAULT_*`) и их конфигурация |
| `pin_validation.[ch]` | Таблица возможностей GPIO ESP32-C6 и валидация пинов |
| `config.[ch]` | `app_config_t`, загрузка/сохранение/валидация NVS, миграция ключей |
| `uart_handler.[ch]` | UART0 (консоль) и UART1 (мост датчиков) |
| `sd_handler.[ch]` | SD/SPI, FatFs, запись с ротацией `sd_write_rotate()` |
| `sensor_handler.[ch]` | Драйверы I2C (SHT21/INA219/INA226), задача логирования, MQTT |
| `http_server.[ch]` | HTTP-сервер, регистрация эндпоинтов, JSON-помощники |
| `web_handlers.[ch]` | Монтирование SPIFFS и отдача статики |
| `log_handler.[ch]` | Кольцевой буфер лога (`esp_log_set_vprintf`) и `GET /logs` |
| `wifi_ap.[ch]` | Инициализация Wi-Fi в режиме AP+STA и SoftAP |
| `wifi_scan.[ch]` | STA: сканирование, подключение, статус, отключение |
| `system_handler.[ch]` | Перезагрузка и сброс к заводским (с CSRF-проверкой Origin) |
| `self_test.[ch]` | Self-test HTTP-эндпоинтов при загрузке |
| `telnet_bridge.[ch]` | TCP→UART0/UART1 ретрансляторы (+ опциональный лог на SD) |

Веб-интерфейс — единый самодостаточный файл `web/index.html` (инлайн CSS + JS).
Матрица тестов — `tests/http_endpoints.csv`; генератор —
`tools/gen_http_tests.py`.

## Процесс внесения изменений

1. Форкните репозиторий `spectrespc/ESP32-OKO-KVM` на GitHub.
2. Создайте ветку с осмысленным именем:

   ```bash
   git checkout -b feature/short-description
   ```

3. Внесите изменения, придерживаясь [стандартов кодирования](#стандарты-кодирования).
4. Соберите проект (`./build_and_flash.sh build`) и убедитесь, что нет
   предупреждений компилятора.
5. Прогоните тесты (`./build_and_flash.sh test` по подключённому к SoftAP
   хосту, а также self-test в мониторе).
6. Обновите `CHANGELOG.md` и `CHANGELOG.ru.md` (см.
   [Обновление CHANGELOG](#обновление-changelog)).
7. Закоммитьте изменения с понятным сообщением (см. ниже) и отправьте ветку:

   ```bash
   git push origin feature/short-description
   ```

8. Откройте Pull Request в ветку `main` с описанием того, что и зачем изменено.

### Стиль сообщений коммитов

Используйте краткий префикс, описывающий область изменения:

```
docs: add Russian documentation
feat: add per-sensor CSV logging
fix: correct SDSPI MISO/SCLK defaults
refactor: extract MQTT publish helper
test: extend HTTP endpoint matrix
build: enable exFAT via ffconf patch
```

Первую строку держите в пределах ~72 символов; при необходимости добавьте
пустую строку и подробное описание.

## Стандарты кодирования

- **Язык:** C11 для кода ESP-IDF (используются `stdatomic.h`, `stdbool.h`).
- **Форматирование:** отступ 4 пробела, без табов; фигурные скобки на той же
  строке; имена в стиле `snake_case`.
- **Типы:** `<stdint.h>` (`uint8_t`, `int32_t`, ...). Значения датчиков —
  целочисленные с фиксированной запятой, чтобы сериализоваться в JSON без потерь.
- **Инициализация:** `app_main()` вызывает подсистемы в строгом порядке
  (NVS → лог → конфигурация → пины → UART → датчики → SD → Wi-Fi AP → STA →
  MQTT → telnet → SPIFFS → HTTP → self-test). Не нарушайте этот порядок без
  веской причины.
- **Логирование:** используйте `ESP_LOGx(TAG, ...)`. Не вызывайте `ESP_LOG`
  внутри обработчика-перехватчика лога (`log_handler.c`) — это приведёт к
  рекурсии.
- **Ошибки:** проверяйте возвращаемые значения `esp_err_t` и логируйте их через
  `esp_err_to_name()`.
- **Строки:** ограничивайте копирование (`strlcpy`, `snprintf`); никогда не
  выводите длину из исходной строки, если буфер мог быть усечён.
- **Потокобезопасность:** общий изменяемый указатель (например дескриптор
  MQTT-клиента) публикуйте атомарно (`_Atomic`, release/acquire). Для
  разделяемых структур используйте мьютексы FreeRTOS.
- **Комментарии:** пишите по существу; не добавляйте комментарии, дублирующие
  код. Публичные функции в заголовках сопровождайте кратким описанием.
- **Секреты:** не коммитьте ключи, пароли и учётные данные.

## Тестирование

### Self-test на устройстве

Запускается автоматически при загрузке через внутренний SoftAP и пишет
результаты `SELF-TEST PASS/FAIL` в консоль. Таблица ожиданий генерируется из
`tests/http_endpoints.csv`. Разрушающие эндпоинты `/system/*` пропускаются,
чтобы устройство не перезагружалось посреди теста.

### Матрица HTTP-эндпоинтов (хост)

```bash
# Хост должен быть подключён к SoftAP ESP32-Gateway (пароль gateway123)
TEST_HOST=192.168.4.1 ./build_and_flash.sh test
```

Скрипт выполняет каждую строку `tests/http_endpoints.csv` через `curl` и
сравнивает код ответа с ожидаемым. Формат CSV:

```
# METHOD,PATH,EXPECTED_STATUS
GET,/config,200
POST,/config,400
GET,/sd/status,503
GET,/wifi/scan,202
```

Оба потребителя (прошивка и хост-скрипт) используют один и тот же CSV, поэтому
тесты остаются синхронными. При добавлении эндпоинта добавьте строку в CSV — и
прошивка, и хост-тест подхватят её автоматически.

## Обновление CHANGELOG

Проект следует [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/) и
[Semantic Versioning](https://semver.org/lang/ru/).

- Новые изменения добавляйте в раздел `## [Unreleased]` файла `CHANGELOG.md`
  (и `CHANGELOG.ru.md`), группируя их по подразделам: `Added`, `Changed`,
  `Deprecated`, `Removed`, `Fixed`, `Security`.
- При выпуске версии замените `[Unreleased]` на `[X.Y.Z] — ГГГГ-ММ-ДД` и
  добавьте новый пустой раздел `[Unreleased]` сверху.
- Формулируйте записи с точки зрения пользователя: что изменилось и почему.
- Обязательно обновляйте **оба** файла — английский и русский.
