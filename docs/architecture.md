# Архитектура системы

Документ описывает внутреннее устройство прошивки ESP32-C6 Gateway: подсистемы,
порядок инициализации, задачи FreeRTOS, карту памяти и стратегию управления
памятью.

## Обзор

Прошивка — самодостаточное приложение ESP-IDF (`app_main()` в `main/main.c`).
Она предоставляет REST API и веб-интерфейс по Wi-Fi, ретранслирует UART в TCP,
пишет на SD-карту, опрашивает I2C-датчики и публикует их показания в MQTT.

```
                        ┌─────────────────────────────┐
                        │        app_main()           │
                        │  (main/main.c, порядок init)│
                        └──────────────┬──────────────┘
                                       │
        ┌──────────────┬───────────────┼───────────────┬──────────────┐
        ▼              ▼               ▼               ▼              ▼
   ┌─────────┐   ┌──────────┐   ┌────────────┐   ┌───────────┐  ┌──────────┐
   │  NVS    │   │  Config  │   │  Pin init  │   │  UART0/1  │  │ Sensors  │
   │ storage │   │  (NVS)   │   │ +validation│   │  console/ │  │ I2C/MQTT │
```

## Подсистемы

### NVS (энергонезависимое хранилище)
Раздел `nvs`. Пространство имён `storage`. Хранит всю конфигурацию, включая
флаги подсистем, адреса I2C-датчиков, назначения GPIO и учётные данные станции
(`sta_ssid` / `sta_password`). Ключи ограничены 15 символами. Загрузка и
сохранение — в `config.c`. Устаревшие ключи telnet мигрируются один раз при
загрузке (двухфазная фиксация).

### Конфигурация (`config.[ch]`)
Глобальная структура `app_config_t` содержит флаги подсистем, GPIO-карту
(`pin_config_t`), адреса INA, строки (Wi-Fi, MQTT) и порты telnet. Изменения
через `POST /config` проходят валидацию (`config_validate_and_set`) и
применяются после перезагрузки.

### Инициализация пинов и валидация (`pins.[ch]`, `pin_validation.[ch]`)
`init_pins()` конфигурирует GPIO согласно `app_config_t`, пропуская отключённые
подсистемы. Таблица возможностей в `pin_validation.c` описывает для каждого GPIO
(0–22) поддержку input/output/open-drain, флаг зарезервированного USB-пина
(12/13) и strapping-пина (2/8/9). Роли `ext_pwr` / `ext_rst` добавлены в таблицу
как выходные (output-only).

### Управление внешним устройством (`ext_control.[ch]`)
Модуль `ext_control.c` управляет двумя GPIO для питания и сброса подключённого
внешнего устройства:

- **Инициализация:** `init_ext_control()` → `init_ext_pins()` (pins.c).
  Вызывается после `init_pins()` в `app_main()`. Восстанавливает персистентное
  состояние питания из NVS, используя `pin_out_glitchless()` для защиты от
  дребезга (уровень защёлкивается до включения выходного драйвера).
- **Переключение питания:** `ext_power_set(on)` устанавливает уровень на пине
  согласно полярности и атомарно пишет состояние в NVS через
  `config_set_ext_power_state()` → `nvs_set_u8` + `nvs_commit`.
- **Импульс сброса:** `ext_reset_pulse()` — блокирующий вызов в контексте
  HTTP-обработчика. Активирует пин на `ext_rst_pulse_ms`, затем деактивирует.
  Троттлинг: не чаще одного импульса в 2 секунды (`EXT_RESET_MIN_INTERVAL_US`).
- **HTTP:** три эндпоинта зарегистрированы в `http_server.c`
  (`/ext/status`, `/ext/power`, `/ext/reset`). POST-эндпоинты используют
  CSRF-защиту `request_is_same_origin()` (system_handler.c).
- **Web UI:** вкладка External (тумблер питания + сброс с подтверждением),
  карточка «External device» на Dashboard, поля в Configuration.

### UART (`uart_handler.[ch]`)
UART0 (GPIO16/17) и UART1 (GPIO4/5) — внешние линии 8N1; консоль прошивки
выводится через USB Serial/JTAG и на эти GPIO не попадает. Скорость берётся из
конфигурации (`baud_rate` для UART0, `uart1_baud_rate` для UART1; по умолчанию
115200/9600) и применяется при старте. Значение вне белого списка (мусор в NVS
или нулевая конфигурация после сбоя `nvs_open`) заменяется константой
`UART0_CONFIG_BAUD_RATE`/`UART1_CONFIG_BAUD_RATE` с предупреждением в лог, чтобы
`uart_param_config()` никогда не получил произвольную скорость. Для обоих UART
устанавливаются буферы TX/RX по 4096 байт; пины задаются конфигурацией.

### Датчики (`sensor_handler.[ch]`)
I2C-шина (порт 0, 100 кГц, внутренние подтяжки, глитч-фильтр 7) с драйверами
SHT21, INA219 и INA226. Если датчик отсутствует или шина отключена, возвращаются
симулированные значения (25.3 °C, 60.5 %, 1013 гПа, 500 лк). Задача
`sensor_log_task` раз в 10 секунд читает датчики, пишет CSV на SD (при
включённых флагах) и публикует MQTT-топики.

### SD-карта (`sd_handler.[ch]`)
SD по SPI (`SPI2_HOST`), FatFs, точка монтирования `/sdcard`. Форматирование при
неудаче монтирования включено (`max_files = 8`). `sd_write_rotate()` ограничивает
файлы 1 МБ и хранит до 10 ротированных копий, удаляя назначение перед
переименованием (обход поведения FatFs `f_rename`, возвращающего `EEXIST`).
`sd_list_dir()` обходит один уровень каталога через `opendir/readdir` (два
прохода: сначала каталоги, затем файлы) и возвращает JSON-массив;
`sd_open_file()` отдаёт `FILE*` для потокового скачивания. Оба помощника
отклоняют `..`, `\` и управляющие символы и работают относительно `/sdcard`.

### Wi-Fi (`wifi_ap.[ch]`, `wifi_scan.[ch]`)
Радио работает в режиме AP+STA. SoftAP всегда включён (SSID по умолчанию
`ESP32-Gateway`, WPA2-PSK, канал 1, до 4 клиентов). Wi-Fi modem sleep отключён
(`WIFI_PS_NONE`): шлюз питается от сети, а сон в AP+STA приводил к
`BEACON_TIMEOUT` через часы работы. Сторона STA сканирует сети, подключается и
переподключается бесконечно: задержка нарастает как 1, 2, 5, 10, 20, 30, 60 с и
далее остаётся 60 с. Счётчик неудач сбрасывается только после получения IP.
После 10 минут непрерывных неудач выполняется мягкий рестарт радио
(`esp_wifi_stop` → 200 мс → `esp_wifi_start`), не чаще одного раза в 10 минут;
SoftAP в это время недоступна 1–2 с, перезагрузки устройства нет. Учётные
данные STA хранятся отдельно от AP.

### NTP и реальное время (`ntp_time.[ch]`)
SNTP из lwIP (`esp_sntp_*`). Запуск идемпотентен и выполняется из обработчика
`IP_EVENT_STA_GOT_IP` (`wifi_scan.c`) — то есть только когда сеть уже доступна.
Режим `SNTP_SYNC_MODE_IMMED`, опрос раз в час, сервер и флаг включения берутся
из конфигурации (`ntp_enable`, `ntp_server`); `POST /system/time` перезапускает
клиент через `esp_sntp_stop()` + `esp_sntp_init()`. Признак синхронизации —
`time(NULL) > 1700000000` (батарейного RTC у ESP32-C6 нет, до синхронизации
CLOCK_REALTIME считает от загрузки). `ntp_stamp()` форматирует локальное время
как `ГГГГ-ММ-ДД ЧЧ:ММ:СС.ммм`, применяя фиксированное смещение
`tz_offset_min` вручную (`gmtime_r` + смещение, без POSIX TZ/DST).
`ntp_time_ms()` отдаёт epoch-мс после синхронизации и аптайм-мс до неё; им
пользуются CSV датчиков, MQTT и `exported_at`. Все внутренние таймеры
(auth-локауты, OTA-интервалы, retry Wi-Fi) работают на `esp_timer_get_time()` и
скачком реального времени не затрагиваются.

### HTTP-сервер (`http_server.c`)
Порт 80, `ctrl_port` 32768, `max_open_sockets` 10, 32 URI-обработчика (лимит
`max_uri_handlers` = 32), backlog 16, wildcard-сопоставление URI, стек задачи
8 КБ, приоритет `tskIDLE_PRIORITY+5`. Пул сокетов LwIP — 20
(`CONFIG_LWIP_MAX_SOCKETS`). Точные REST-маршруты регистрируются
раньше catch-all `/*`, поэтому они выигрывают сопоставление. Настройки ответов —
8 заголовков, recv/send таймауты 10 с.

### Веб-интерфейс (`web_handlers.c`, `web/index.html`)
SPA — единый `index.html`, встроенный в образ приложения на этапе сборки
(`EMBED_FILES` в `main/CMakeLists.txt`) и отдаваемый обработчиком статики прямо
из `.rodata`. Поэтому веб-интерфейс обновляется тем же OTA-образом, что и
прошивка, и не может разойтись с версией REST API.
Path traversal (`..`) отклоняется с `400`.

### Telnet-мосты (`telnet_bridge.c`)
Два независимых ретранслятора TCP→UART (bridge0→UART0, bridge1→UART1). Каждый
слушает на `0.0.0.0` (доступен и из SoftAP 192.168.4.1, и из LAN через
STA-адрес), обслуживает одного клиента за раз, с `SO_SNDTIMEO` 5 с, буфером
256 байт и повторными попытками привязки каждые 5 с. Мост не зависит от
появления IP у SoftAP и стартует сразу, в том числе при поднятом только STA.
Мост выполняет минимальный Telnet-handshake: при подключении шлёт `WILL ECHO` и
`WILL SGA`, вырезает IAC-последовательности из потока клиента (состояние
парсера переживает границы `recv()`) и удваивает `0xFF` в потоке UART→клиент.
Сырые TCP-клиенты (`nc`) увидят 6 приветственных байт. Аутентификации нет:
ретранслятор без шифрования нельзя выставлять в интернет.

При включённом `uartN_sd_log` тот же поток дублируется в `/sdcard/uarN.log`
(функция `sd_log_write`). Байты в файл попадают только пока клиент подключён,
потому что `uart_read_bytes()` вызывается единственным потребителем внутри
`relay_loop`. Формат выбирается полем `uartN_sd_log_fmt`: raw (как есть),
text (префикс `[<мс>ms] RX/TX:` до синхронизации SNTP и
`[ГГГГ-ММ-ДД ЧЧ:ММ:СС.ммм] RX/TX:` после неё, плюс `\xNN` для непечатаемых
байтов) или hexdump (16 байт в строке с ASCII-колонкой). Форматирование идёт срезами по 128 байт в
статический буфер контекста моста; TX логируется после вырезания IAC, поэтому
содержимое совпадает с тем, что уходит в UART, а удвоение `0xFF` для клиента на
файл не влияет.

### Системный лог (`log_handler.c`)
Кольцевой буфер в RAM на 128 строк по 160 символов. Перехватывает вывод через
`esp_log_set_vprintf()`, защищён мьютексом. `GET /logs` возвращает
`{"logs":[...]}`. Метка строки формируется самим ESP_LOG по источнику
`CONFIG_LOG_TIMESTAMP_SOURCE_SYSTEM` (`sdkconfig.defaults`): после
синхронизации это время суток UTC, до неё — малые значения от загрузки.

### MQTT (`sensor_handler.c`)
`esp-mqtt` из ESP Component Registry. Дескриптор клиента — атомарный указатель
(C11 `_Atomic`), публикуется только после успешного запуска. Одна JSON-полезная
нагрузка на датчик, QoS 0.

### OTA (`ota_handler.[ch]`)
Фоновая задача (`ota`, стек 8192, приоритет 4) выполняет проверки и установку;
ручные команды приходят через `xTaskNotify` из `/ota/check` и `/ota/update`.
Манифест `{ota_url}/version.json` разбирается cJSON, версии сравниваются
встроенным `semver_parse`/`semver_cmp` (строго 3 компонента). Периодические
проверки идут только при `ota_enable` + непустом `ota_url`, с интервалом
`ota_check_interval_min`; ручные проверки троттлятся до одной в 5 с.

Установка: `esp_http_client` → `esp_ota_begin(OTA_WITH_SEQUENTIAL_WRITES)` →
`esp_ota_write` + инкрементальный SHA-256 (PSA Crypto, `psa_hash_*`) →
сверка с манифестом → `esp_ota_end` → `esp_ota_set_boot_partition` →
`esp_restart`. При любой ошибке вызывается `esp_ota_abort`, текущий слот
остаётся активным. Целевой раздел — `esp_ota_get_next_update_partition()`
(чередование `ota_0` ↔ `ota_1`).

`GET /ota/slots` отдаёт версии и состояния обоих слотов (описание читается
через `esp_ota_get_partition_description()`, состояние — через
`esp_ota_get_state_partition()`). `POST /ota/slot` проверяет, что выбранный
слот не является работающим и содержит читаемый образ, вызывает
`esp_ota_set_boot_partition()` и перезагружает устройство; во время работы
OTA-воркера переключение блокируется.

Rollback: `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y` — новый образ стартует как
`PENDING_VERIFY`; `self_test.c` подтверждает его
(`esp_ota_mark_app_valid_cancel_rollback`) только после полностью успешного
набора HTTP-проверок. Если прошивка не подтвердилась, следующая перезагрузка
возвращает предыдущий слот. При запуске из legacy-раздела `factory` (старая
раскладка) подтверждение пропускается.

## Порядок инициализации

`app_main()` инициализирует подсистемы строго по порядку (важно для зависимостей):

1. **NVS** (`nvs_flash_init`)
2. **Кольцевой буфер лога** (`init_log_handler`) — как можно раньше, чтобы
   поймать сообщения загрузки
3. **Конфигурация** (`init_config`) — должна предшествовать пинам и флагам
4. **Пины** (`init_pins`)
5. **Внешнее управление** (`init_ext_control`) — конфигурирует GPIO питания и
   сброса и восстанавливает персистентное состояние из NVS; следует за
   `init_pins()`
6. **UART0 / UART1** (`init_uart0` / `init_uart1`) — по флагам `uartN_enable`
7. **Датчики** (`init_sensor_handler`) — если включена подсистема датчиков, I2C,
   любое CSV-логирование или MQTT
8. **SD-карта** (`init_sd_handler`) — по флагу `sd_enable`
9. **Wi-Fi AP** (`wifi_init`) — базовая инфраструктура
10. **Wi-Fi STA** (`init_wifi_sta`) — восстановление сохранённой сети; SNTP
    (`ntp_time_start`) стартует позже, из события `IP_EVENT_STA_GOT_IP`
11. **MQTT** (`init_mqtt`) — после появления сетевого стека
12. **OTA** (`init_ota`) — фоновая задача; периодические проверки только при
    `ota_enable` и заданном `ota_url`
13. **Telnet-мосты** (`init_telnet_bridge0/1`) — если включены и доступен их UART
14. **HTTP-сервер** (`init_http_server`)
15. **Self-test** (`start_self_test`) — при успехе подтверждает OTA-образ

После инициализации задача `app_main` остаётся живой в цикле задержки.

## Задачи и приоритеты

Приоритеты FreeRTOS (`CONFIG_FREERTOS_HZ=100`):

| Задача | Где создаётся | Стек | Приоритет |
|--------|---------------|------|-----------|
| `app_main` (main task) | ESP-IDF | 8192 | по умолчанию (affinity 0) |
| `httpd` (HTTP-сервер) | `http_server.c` | 8192 | `tskIDLE_PRIORITY+5` |
| `sensor_log` | `sensor_handler.c` | 4096 | 5 |
| `telnet_bridge0/1` | `telnet_bridge.c` | 4096 | 5 |
| `ota` | `ota_handler.c` | 8192 | 4 |
| `wifi_sup` | `wifi_scan.c` | 4096 | 4 |
| `self_test` | `self_test.c` | 8192 | 5 |

Периоды и таймауты:

- `sensor_log` — раз в 10 с (`SENSOR_LOG_INTERVAL_MS`).
- `self_test` — стартует через 3 с после загрузки; HTTP-запросы с таймаутом 5 с.
- `ota` — периодическая проверка раз в `ota_check_interval_min`; ручные
  проверки не чаще одной в 5 с.
- `wifi_sup` — тик 1 с; таймаут подключения (ассоциация + DHCP) 25 с; проверка
  IP раз в 10 с; RSSI-лог раз в 60 с.
- Теlnet — буфер 256 байт, retry привязки 5 с, пауза между клиентами 500 мс,
  `SO_SNDTIMEO` 5 с.
- I2C-транзакции — таймаут 100 мс (SHT21 hold-master до ~85 мс).

## Карта памяти и разделы

Плата ESP32-C6FH4, 4 МБ встроенной флеш-памяти
(`CONFIG_ESPTOOLPY_FLASHSIZE_4MB=y`), пользовательская таблица разделов
(`partitions.csv`):

| Имя | Тип | Смещение | Размер | Назначение |
|-----|-----|----------|--------|------------|
| (partition table) | — | 0x8000 | 0x1000 | Таблица разделов |
| `nvs` | data/nvs | 0x9000 | 0x6000 (24 КБ) | Конфигурация |
| `otadata` | data/ota | 0xF000 | 0x2000 (8 КБ) | Данные OTA |
| `phy_init` | data/phy | 0x11000 | 0x1000 (4 КБ) | Калибровка PHY |
| `ota_0` | app/ota_0 | 0x20000 | 0x1A0000 (1.625 МБ) | OTA-слот A |
| `ota_1` | app/ota_1 | 0x1C0000 | 0x1A0000 (1.625 МБ) | OTA-слот B |
| `spiffs` | data/spiffs | 0x360000 | 0xA0000 (640 КБ) | Резерв (не используется с 1.7.0; веб-интерфейс встроен в приложение) |

A/B-схема: `esp_ota_get_next_update_partition()` чередует `ota_0` и `ota_1`;
раздела `factory` нет, поэтому оба слота доступны для OTA-записи.
`nvs` и `otadata` остались на прежних смещениях, поэтому переход со старой
таблицы (2.5 МБ factory + 1.375 МБ SPIFFS) через обычный `idf.py flash`
сохраняет настройки. `idf.py flash` также пишет `ota_data_initial.bin`, поэтому
после прошивки загружается `ota_0`.

Раскладка `factory` + `ota_0` (до 1.4.3) поддерживала только одно OTA:
после загрузки из `ota_0` следующий целевой раздел совпадал с работающим и
`esp_ota_begin()` возвращал `ESP_ERR_OTA_PARTITION_CONFLICT`. Переход на
`ota_0` + `ota_1` требует однократной прошивки по USB; смещение `nvs` не
меняется. С 1.7.0 веб-интерфейс встроен в образ приложения, поэтому раздел
`spiffs` больше не используется и остаётся зарезервированным.

Начиная с 1.7.0 отдельный образ SPIFFS не собирается и не прошивается:
`web/index.html` включается в приложение через `EMBED_FILES` и обновляется
вместе с ним по OTA.

## Управление памятью

- **Строки конфигурации** (`wifi_ssid`, `wifi_password`, `server_url`, MQTT URL
  и префикс, `ota_url`) выделяются через `malloc`/`strdup` и освобождаются в
  `set_config` и перед повторной загрузкой в `load_config`.
- **HTTP-обработчики** читают тело запроса в стековые буферы (4096 байт для
  `/config`, 512 — для `/sd/write` и `/sensor`, 256 — для `/wifi/connect`) и
  используют cJSON для разбора; JSON-строки освобождаются после отправки.
- **Кольцевой буфер лога** — статический массив `[128][160]` в `.bss`
  (около 20 КБ).
- **Буферы форматирования SD-логов** — по одному `char[1024]` в контексте
  каждого Telnet-моста (`.bss`, +2 КБ суммарно). В стек задачи моста (4096
  байт) они не помещаются вместе с буфером ретрансляции.
- **MQTT-дескриптор** — атомарный указатель; клиент уничтожается при неудачном
  старте до публикации дескриптора, что исключает use-after-free.
- **json-снимки** (`/wifi/scan/results`, `/logs`) копируются под мьютексом и
  сериализуются вне блокировки, чтобы не держать её при аллокациях.
- **Стеки задач** заданы фиксированно (см. таблицу выше); крупные буферы не
  размещаются в стеке задач HTTP-сервера.
