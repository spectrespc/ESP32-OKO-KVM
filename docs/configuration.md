# Справочник конфигурации

Вся конфигурация хранится в энергонезависимой памяти NVS в пространстве имён
`storage`. Документ описывает параметры, формат JSON для `POST /config`,
семантику частичного обновления, переназначение GPIO, валидацию, миграцию
устаревших ключей и сброс к заводским настройкам.

> кодом `BAUD_INVALID`. Новое значение применяется после перезагрузки.

## Формат SD-логов UART-трафика

Файлы `/sdcard/uar0.log` и `/sdcard/uar1.log` пополняются только пока к
соответствующему Telnet-мосту подключён клиент: UART читается единственным
потребителем внутри `relay_loop`. Без клиента трафик не записывается.

Режим задаётся отдельно для каждого UART полями `uart0_sd_log_fmt` и
`uart1_sd_log_fmt` (NVS-ключи `u0_log_fmt`/`u1_log_fmt`):

| Значение | Режим | Формат |
|----------|-------|--------|
| `0` | raw | Байты как есть (поведение до 1.7.0) |
| `1` | text (по умолчанию) | `[<мс>ms] RX: текст` / `[<мс>ms] TX: текст`; печатаемые ASCII, `\n` и `\r` — как есть, остальные байты — `\xNN` |
| `2` | hexdump | `[<мс>ms] RX 0000: NN NN … |ascii|`, по 16 байт в строке |

Время в префиксе — локальное реальное время `[ГГГГ-ММ-ДД ЧЧ:ММ:СС.ммм]`
(со смещением `tz_offset_min`) после первой успешной синхронизации SNTP. До неё
(а также если NTP выключен или сервер недоступен) пишется аптайм `[<мс>ms]`,
поэтому смешанные метки в начале файла — ожидаемое поведение. `RX` — данные от
внешнего устройства к клиенту, `TX` — от клиента к устройству (уже после
вырезания Telnet IAC). Форматированный вывод примерно в 4 раза объёмнее raw,
поэтому ротация файла наступает раньше; лимиты
`LOG_ROTATE_MAX_SIZE`/`LOG_ROTATE_DEPTH` не меняются. Значение `3` и выше
отклоняется кодом `LOG_FMT_INVALID`; формат применяется после перезагрузки
(мост читает его при старте задачи).

## NTP-синхронизация и метки времени

- `ntp_enable` (NVS `ntp_en`) — SNTP-клиент, по умолчанию включён.
- `ntp_server` (NVS `ntp_srv`) — имя хоста длиной 1–63 символа из набора
  `A-Za-z0-9._-`; по умолчанию `pool.ntp.org`. Для изолированной локальной сети
  укажите адрес роутера или локального NTP-сервера.
- `tz_offset_min` (NVS `tz_min`) — фиксированное смещение UTC в минутах,
  −720…+840 (по умолчанию 180, московское время). Летнее время (DST) не
  поддерживается: смещение не меняется в течение года.

Синхронизация запускается при первом получении IP станцией
(`IP_EVENT_STA_GOT_IP`) и далее опрашивает сервер по UDP 123 раз в час. Если
интернета нет или UDP 123 закрыт, устройство продолжает работать с
аптайм-метками без деградации. `GET /system/time` показывает состояние часов,
`POST /system/time` запускает внеочередную синхронизацию.

`ntp_enable` и `ntp_server` применяются после перезагрузки. `tz_offset_min`
действует сразу: форматтеры читают конфигурацию при каждой записи.

Семантика меток:

- `/sdcard/uarN.log`: `[ГГГГ-ММ-ДД ЧЧ:ММ:СС.ммм]` после синхронизации,
  `[<мс>ms]` аптайма до неё.
- CSV датчиков: `ts_ms` — epoch-миллисекунды после синхронизации, иначе
  миллисекунды с момента загрузки. Один столбец может содержать оба вида;
  скачок виден на первой синхронизации. Поле `ts` в MQTT-сообщениях следует
  тому же правилу.
- `GET /config/export`: `exported_at` — epoch-секунды после синхронизации,
  иначе секунды с момента загрузки.
- Системные логи ESP_LOG используют `CONFIG_LOG_TIMESTAMP_SOURCE_SYSTEM`:
  после синхронизации печатается время суток UTC (`ЧЧ:ММ:СС.ммм`), до неё —
  малые значения от загрузки. Смещение `tz_offset_min` к системным логам не
  применяется.

## Учётные данные Web UI

Web-креды хранятся отдельно, в пространстве имён NVS `auth`:

| Ключ | Тип | По умолчанию | Примечания |
|------|-----|--------------|------------|
| `user` | str | `admin` | Логин Web UI |
| `pass` | str | случайный (генерируется при первом старте) | Хеш пароля (64 hex-символа), без соли |

По умолчанию пароль Web UI **не** `admin`: при первой загрузке генерируется
случайный 24-символьный пароль и один раз печатается в консоль USB Serial/JTAG
(`Created credentials: user 'admin', password '...'`). Если в NVS остался старый
пароль `admin`, в журнале появляется предупреждение. WiFi AP по умолчанию:
`ESP32-Gateway` / `gateway123`.
Смена производится через `POST /auth/password` или вкладку **Account**;
она завершает все активные сессии.

## Формат JSON для `POST /config`

- `Content-Type: application/json`, тело ≤ 4096 байт.
- Флаги включения — целое `0` или `1`.
- Пины — целые в диапазоне `0`–`22`, вложенные в объект `"pins"`.
- Адреса INA — целые `0x40`–`0x4F` (`64`–`79`).
- Строки ограничены по длине (см. таблицу выше).

Успех всегда:

```json
{"message":"Configuration saved. Reboot to apply."}
```

## Частичное обновление конфигурации

`POST /config` — это **частичное** обновление: изменяются только поля,
присутствующие в теле запроса; остальные сохраняют текущие значения. Если тело
пустое или не содержит ни одного распознанного поля, возвращается `400`:

```json
{"error":"No valid configuration fields provided"}
```

Пример комбинированного обновления:

```bash
curl -X POST http://192.168.4.1/config \
  -H 'Content-Type: application/json' \
  -d '{
        "i2c_enable": 1,
        "sht21_enable": 1,
        "ina219_enable": 1,
        "ina219_addr": 65,
        "sht21_sd_log": 1,
        "mqtt_enable": 1,
        "mqtt_broker_url": "mqtt://192.168.1.10:1883",
        "mqtt_topic_prefix": "gateway"
      }'
```

> Изменения сохраняются в NVS немедленно, но **применяются после перезагрузки**.
> Используйте `POST /system/reboot`.

### Числовые значения вне диапазона

Нецелые значения или значения вне допустимого диапазона для числового поля
приводят к `400`:

```json
{"error":"Numeric value out of range"}
```

### Слишком длинные строки

```json
{"error":"String too long (wifi_ssid<=31, wifi_password<=63, server_url<=255, mqtt_broker_url<=255, mqtt_topic_prefix<=64, ota_url<=255, ntp_server<=63)"}
```

## OTA-обновления

```bash
curl -X POST http://192.168.4.1/config \
  -H 'Content-Type: application/json' \
  -d '{"ota_enable":1,"ota_url":"http://192.168.1.10:8000","ota_check_interval_min":360}'
```

- `ota_url` — база, по которой сервер отдаёт `version.json` и образ `.bin`.
  HTTPS не поддерживается: используйте доверенную локальную сеть.
- `ota_check_interval_min` — 5…10080 минут (по умолчанию 360 = 6 часов).
- `ota_enable` включает только *периодическую проверку*; установка всегда
  выполняется вручную (`POST /ota/update` или вкладка **Update**).
- Изменения применяются после перезагрузки.

Формат манифеста и пример сервера — в [`api.md`](api.md) и README
(`tools/ota_server.py`). Целостность образа проверяется по SHA-256; при
несовпадении или обрыве загрузки текущая прошивка остаётся активной.

## Переназначение GPIO на лету

Любую роль GPIO можно переназначить через объект `"pins"`. Заводские значения —
лишь стартовая точка.

```bash
curl -X POST http://192.168.4.1/config \
  -H 'Content-Type: application/json' \
  -d '{"pins":{"led_red":20,"led_green":21}}'
```

Правила:

- Каждый пин должен быть уникален (кроме петель — см. валидацию).
- Пин должен поддерживать требуемое направление.
- I2C-пины должны поддерживать open-drain.
- GPIO 12/13 нельзя назначать при активной USB-консоли.
- Изменения вступают в силу после перезагрузки.

## Валидация

Валидация выполняется в `config_validate_and_set()` (конфигурация + конфликты) и
`validate_pin_config()` (возможности пинов). При ошибке весь запрос отклоняется
с `400` и кодом в поле `"error"`.

### Коды ошибок пинов

| Код | Условие |
|-----|---------|
| `PIN_INVALID` | GPIO вне диапазона 0–22 (или `null`-конфигурация) |
| `PIN_NO_CAPABILITY` | GPIO не поддерживает требуемое направление или open-drain |
| `PIN_USB_CONFLICT` | GPIO 12/13 при активной консоли USB Serial/JTAG |
| `PIN_DUPLICATE` | Один GPIO назначен двум ролям |
| `PIN_I2C_CONFLICT` | I2C SDA и SCL — один и тот же GPIO |

### Коды ошибок конфигурации

| Код | Условие |
|-----|---------|
| `ADDR_INVALID` | `ina219_addr` или `ina226_addr` вне `0x40`–`0x4F` |
| `BAUD_INVALID` | `baud_rate` или `uart1_baud_rate` вне белого списка скоростей |
| `I2C_CONFLICT` | Включены оба INA219 и INA226; либо включённый INA использует `0x40` вместе с включённым SHT21 |
| `LOG_FMT_INVALID` | `uart0_sd_log_fmt` или `uart1_sd_log_fmt` больше `2` |
| `PORT_INVALID` | `telnet0_port` или `telnet1_port` равно `0` |
| `PORT_CONFLICT` | Оба telnet-моста включены на одном порту |
| `UART_INVALID` | Telnet-мост включён при выключенном соответствующем UART |
| `MQTT_INVALID` | MQTT включён без непустого URL брокера или URL длиннее 255 символов |
| `EXT_INVALID` | `ext_rst_pulse_ms` вне диапазона 10–5000; `ext_pwr_pol` / `ext_rst_pol` не `0`/`1` |
| `OTA_INVALID` | `ota_check_interval_min` вне диапазона 5–10080 или `ota_url` длиннее 255 символов |
| `NTP_INVALID` | При включённом NTP `ntp_server` пуст или не проходит белый список символов; `tz_offset_min` вне диапазона −720…840 |

### Флаг strapping-пинов

GPIO 2, 8 и 9 можно назначать, но при этом пишется предупреждение в лог — их
состояние влияет на режим загрузки. Валидация их не отклоняет.

## Telnet-мосты

`telnet0_enable` / `telnet1_enable` включают мосты TCP→UART0 и TCP→UART1
(порты задаются в `telnet0_port` / `telnet1_port`). Мост стартует только при
включённом соответствующем `uartN_enable`.

Каждый мост слушает на `0.0.0.0`, поэтому доступен и с клиента SoftAP
(`192.168.4.1`), и из LAN по STA-адресу устройства. Если оба моста включены,
их порты должны различаться, иначе `POST /config` вернёт `PORT_CONFLICT`.

Ключи конфигурации не меняются. Мост выполняет минимальный Telnet-handshake
(`WILL ECHO` / `WILL SGA`), вырезает IAC-команды клиента и удваивает `0xFF` в
направлении UART→клиент; сырые TCP-клиенты (`nc`) увидят 6 приветственных
байт. Аутентификации и шифрования нет — не выставляйте порты в интернет.

Мост не зависит от появления IP у SoftAP: он начинает слушать порт сразу после
загрузки, в том числе когда поднят только STA. Если порт занят, привязка
повторяется каждые 5 с.

## Миграция устаревших ключей (telnet legacy)

Ранние версии использовали единый telnet-мост с ключами `telnet_enable`,
`telnet_port` и `telnet_uart` (0 = UART0, 1 = UART1). При загрузке выполняется
одноразовая миграция:

1. Если присутствует старый ключ `telnet_enable`, а нового `telnet0_en` нет,
   конфигурация «переселяется» на соответствующий UART:
   - `telnet_uart == 0` → значения уходят в `telnet0_enable` / `telnet0_port`;
   - иначе → значения уходят в `telnet1_enable` / `telnet1_port`.
2. Новые ключи пишутся и фиксируются; **ключ-маркер `telnet0_en` пишется
   последним**.
3. Только после успешной фиксации новых ключей стираются устаревшие
   (`telnet_enable`, `telnet_port`, `telnet_uart`).

Если запись новых ключей не удалась, устаревшие ключи сохраняются для следующей
загрузки (миграция повторится). Это гарантирует, что миграция выполнится ровно
один раз и без потери данных.

## Сброс к заводским настройкам

```bash
curl -X POST http://192.168.4.1/system/reset
```

Обработчик стирает раздел NVS (`nvs_flash_erase()`), что сбрасывает всю
конфигурацию к заводским значениям, и перезагружает устройство. Ответ
`{"status":"resetting"}` отправляется до перезапуска.

> Сброс удаляет также учётные данные станции (`sta_ssid` / `sta_password`) и
> Web-креды (пространство `auth`), поэтому после перезагрузки снова действуют
> `admin` / `admin`. SoftAP вернётся к значениям по умолчанию
> (`ESP32-Gateway` / `gateway123`).

## Резервное копирование и восстановление

- **Экспорт:** `GET /config/export` скачивает файл `gateway-config.json` с
  обёрткой `{"format":1,"firmware_version":...,"exported_at":...,"config":{...}}`.
  Вложенный `config` совпадает с `GET /config` (без паролей). `GET /config`
  по-прежнему отдаёт «голый» объект для веб-интерфейса.
- **Импорт:** передайте те же поля в `POST /config`. Отсутствующие поля не
  изменяются. Автоматический импорт файла не поддерживается.
- `wifi_password` и `sta_password` в экспорт не попадают — задавайте их
  отдельно.
